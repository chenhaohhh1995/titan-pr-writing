## 信息核实规则（全流程通用）

写作过程中遇到以下情况，**必须先上网检索，多信息来源交叉验证，网上确实找不到再问用户**：

- 产品型号的参数、技术规格不明确或需核实
- 合作伙伴/嘉宾的名称、背景、合作细节不清楚
- 行业术语、技术概念（如"AMD 千帧电竞""DyDs 2.0"等）需要准确理解
- 竞品信息、市场价格等需要参考
- **游戏/影视/IP 作品的基本信息**（发售日期、背景设定、核心特色、平台等）——书面描写游戏画面时最容易凭训练数据脑补，必须检索确认后再写

**信息检索流程**：
1. **多渠道搜索**：针对同一信息点，从不同关键词、不同角度多次检索
2. **交叉验证**：至少对比 2-3 个独立来源，确认信息一致性后再采纳
3. **优先一手来源**：品牌官网、电商官方旗舰店、权威评测机构 ＞ 自媒体/论坛/二手转述

**搜索工具选择**：详见 `references/联网检索工具说明.md`。

**搜索后处理**：将搜索结果汇总为简短要点，标注信息来源，作为写作素材。多源信息一致 → 直接采纳；信息矛盾 → 优先一手来源或再搜一轮。只有搜索确实找不到或结果严重矛盾时，才向用户确认。

**基础资料数据版本追踪**：用户提供的 briefing/简报中的数字可能在项目周期内更新（如门店数从 160→220）。写作时以最新版本为准，如发现同一数据点在 briefing 与用户后续消息中不一致，优先采用**用户最新消息中的数字**并主动标注差异（"该数据此前为 X，已按最新 briefing 更新为 Y"）。

### 重灾区：游戏/IP 背景描写的核实

**问题**：AI 在描写游戏画面时，训练数据中可能混入了其他游戏的信息（如将前作的墨西哥地图脑补到新作中），导致大段描写完全错误且细节越丰富越显真实。

**规则**：
1. 稿件涉及任何具体游戏/IP 的画面描写（地图、赛道、季节、光照、车型等），必须先检索确认游戏的实际背景设定
2. 检索关键词至少包括：游戏全名 + 发售日期 + 地图/背景/设定 + 核心特色
3. 不凭"印象"或"常识"描写——前作的地图不等于新作的地图
4. 描写中出现的每一个具象地名（如"墨西哥赛道""涩谷十字路口""富士山麓"）都必须是检索确认过的，不在检索结果中的地名一律不写

**典型案例**：2026 年 5 月写《极限竞速：地平线 6》稿件，AI 凭训练数据脑补游戏背景为"墨西哥"（实际为日本），写出"墨西哥赛道""沙漠赛段""沙石纹理"等大段错误描写。地平线 5 是墨西哥，地平线 6 是日本——训练数据混淆了两代作品。

## AI 写作高频错误清单

以下错误来自实际协作中的反复踩坑，每次出稿前逐项自查：

| # | 错误类型 | 表现 | 预防 |
|---|---------|------|------|
| 1 | **游戏/IP 背景脑补** | 凭训练数据编造游戏地图、场景、设定，细节越丰富越显真实但全错 | 涉及游戏画面描写前必须检索确认，前作 ≠ 新作 |
| 2 | **竞品品牌混入** | 把 briefing 中出现的所有品牌一股脑写进稿子，包括显示器/外设/芯片/投影等硬件竞品 | 写之前先把 briefing 中的品牌分为"泰坦军团""游戏/平台方""硬件竞品（删）""用户指定要提的品牌"四类 |
| 3 | **开篇主角错位** | 品牌在开篇段落被埋没或延迟到第二段 | 标准写法首句主语为泰坦军团；赛事宣告型例外允许赛事先行的同时品牌必须在开篇段第二句之前登场 |
| 4 | **标题逻辑断裂** | 显示器"共驰赛道""驰骋赛场"——主语和谓语不匹配 | 显示器可做：还原、呈现、助力、点亮、承载、接住 |
| 5 | **产品自说自话** | 产品段写完成参数就结束了，缺少第三方视角佐证 | 产品介绍后紧跟一段"现场反馈"——玩家反应、讨论热度、排队情况 |
| 6 | **结尾空洞表态** | "让我们一起期待""相信未来会更好" | 用具体内容收束：回顾→展望路线图 / 从...到... 升华 / 多受众收尾；同一模式不连续三篇重复 |
| 7 | **未授权的 KOL/嘉宾段落** | 把 briefing 中的 UP 主、嘉宾信息默认写入，用户未要求就是冗余 | 只写用户明确要求保留的内容 |
| 8 | **活动信息堆砌** | 把 briefing 中所有活动环节（集章/抽奖/CDK/直播/报名入口）不分主次塞进正文 | 只保留对泰坦军团叙事有价值的活动信息，报名入口/购票方式等运营细节按需精简 |
| 9 | **信息倒挂** | 产品还没展开就先讲合作深度、行业意义 | 合作背景为产品服务，开篇后第二段 2-3 句交代即止，产品讲完再收回行业视角 |
| 10 | **段落塞车** | 一个大段塞入光学+眼追+面板+背光+算法五层技术 | 一段只讲一个技术点，每段 2-3 句上限，眼追/面板/背光/算法/色彩各自独立成段 |
| 11 | **开局否定句** | "这不是XX的第一次合作""XX并非偶然" | 直接正面陈述，不绕弯否定。**注意：此规则仅限开篇段落**，结尾否定式拔高（"这并非单纯的多机型陈列，而是…"）是合理的升华修辞，不受此限 |
| 12 | **展品及行为脑补** | 凭产品资料适配名单编造展会实际展出的游戏和内容；凭想象编造玩家的具体行为细节（如"来回拨动数次才肯离手""工作人员多次加开体验时段"） | 展会实际展出内容必须有用户确认或一手来源，不得将"已适配"等同于"现场展出"；现场反馈优先使用玩家自然口语（如"拉枪手感完全不一样""丝滑到不真实"），不编造行为细节 |
| 13 | **飞书标题被覆盖** | 飞书 wiki 节点创建时标题带日期（如`0720【展会预告】...`），但 `docs +update overwrite` 写入 markdown 后，正文 H1 标题（不带日期）自动同步覆盖了 wiki 节点标题，导致日期丢失 | `--title` 参数与 markdown 正文 `# ` 一级标题**必须完全一致**，日期前缀两端都要有；写完 overwrite 后立即用 `wiki +node-get` 验证标题无误 |
| 14 | **产品参数凭记忆填写** | 凭训练数据写出产品参数，未经核实——如 M27E6V-3D 刷新率写 190Hz，实际为 185Hz | 每个技术参数（刷新率/响应时间/亮度/色域/分区数等）必须多源交叉验证后再写入，不凭"印象"填数字。**典型案例**：2026 年 7 月 ChinaJoy 预告稿，AI 将 M27E6V-3D 刷新率写为 190Hz，终稿修正为 185Hz |

## PR 稿件写作红线（全类型通用）

以下规则来自实际写作中的反复踩坑，每次出稿前必须自查：

### 1. 硬件竞品品牌不提
PR 稿以泰坦军团为主角。**非用户明确要求，任何其他硬件品牌不得出现**——包括但不限于显示器、外设、芯片、投影、电视等厂商。游戏/内容/平台方（如 Steam、Xbox、完美世界竞技平台）不构成硬件竞争，可视情况提及。

### 2. 开篇段落内品牌必须在显要位置登场
标准写法：开篇第一句主语为"泰坦军团"。**赛事宣告型开篇例外**——当需要制造开篇爆发力时，允许赛事全称+规模数字阵列先行（如"X赛事——28天、220家门店、30所高校…迎来终极一战"），泰坦军团紧随第二句登场。底线：品牌必须在开篇段落内出现，不得被埋没或延迟到第二段。

### 3. 标题主语-谓语逻辑自洽
标题中主语与谓语必须有合理的逻辑关系。显示器不能"共驰赛道"、不能"驰骋赛场"——它不是车也不是人。显示器可以"还原赛道""呈现竞速""护航赛事""点亮舞台"。

### 4. 产品介绍后必须紧跟玩家/用户评价
写完产品参数和体验描写后，需要一段"现场反馈"段落——玩家上手后的真实反应、讨论热度、具体场景中的评价。用现场反馈为产品力做第三方佐证，避免自说自话。

### 5. 结尾必须落到具体行动或未来方向
结尾不得写"相信未来会更好""让我们一起期待"等空洞表态。**核心原则：用具体内容收束，不固定单一模式。** 可选路径包括：升华收束（从…到…）、多受众收尾（对 X 而言…对 Y 而言…）、回顾→展望三段式（回顾事实 → 行业定位 → 未来路线图）。**展望型结尾（产品路线图/技术迭代方向/生态深化计划）优先推荐**——以品牌接下来要做的事收束，比抽象拔高更有力量。同一模式不得连续三篇重复使用。

## 标准流程（6 步）

> 完整流程细节以 `SKILL.md` 为权威版本，本文件保留概要。

### Step 1 — 接收 Briefing + 类型判定
输入：
- 产品方/市场部提供的 briefing（活动信息、主推产品、嘉宾/合作伙伴）
- 竞品近期同类稿件（可选，用于差异化参考）

输出：
- 一句话的核心主题
- 确定本次属于哪种稿件类型 + 子类型

### Step 2 — 信息挖掘与缺口分析
对照 `SKILL.md` §各类型必备信息清单，逐项标记已有/缺失。缺失信息先上网检索，检索不到的整理为编号确认清单提交用户。**用户逐条确认后**方可进入 Step 3。

### Step 3 — 搭骨架
从对应骨架文件的大纲变体中选 3 套候选，分别生成具体大纲，交给用户挑选。

### Step 4 — 填内容
用户确认大纲后，按 `references/行文措辞说明文档.md` 的声线和句式产出正文：
1. 先写产品介绍（量最大的部分，遵循定位→技术→体验→品质句模式）
2. 再写开篇（事件宣告或数据引爆或定位宣言，按 §9 选择）
3. 写结尾
4. 最后润色标题

### Step 5 — 自查 + 反馈
按骨架文件的 Checklist 逐项核对。

核完后交给需求方（市场部/产品部）确认：
- 产品参数是否准确
- 活动信息是否正确
- 价格/福利/奖项表述是否 OK

### Step 6 — 定稿
修改反馈后，将终稿保存到对应类型文件夹，命名格式：

`【赛事直击】YYYYMMDD_品牌_赛事_看点.docx`（赛事助阵·直击）
`【赛事预告】YYYYMMDD_品牌_赛事_平台.docx`（赛事助阵·预告）
`【展会直击】YYYYMMDD_品牌_展会_看点.docx`（展会参展·直击）
`【展会预告】YYYYMMDD_品牌_展会_看点.docx`（展会参展·预告）
`【直播预告】YYYYMMDD_品牌_主题_平台.docx`（直播预热）
`【电竞新品】YYYYMMDD_品牌_系列名_技术亮点.docx`（新品发布）
`【校园巡展】YYYYMMDD_品牌_学校_看点.docx`（校园巡展）
`【深度结盟】YYYYMMDD_品牌_合作方_主题.docx`（战略合作·已签）
`【重磅合作】YYYYMMDD_品牌_合作方_主题.docx`（合作落地·产品被指定）
`【生态共建】YYYYMMDD_品牌_合作方_主题.docx`（生态共建·多场景长期协同）
`【竞逐新程】YYYYMMDD_品牌_合作方_主题.docx`（战队赞助官宣）
`【深度结盟】YYYYMMDD_品牌_合作方_主题.docx` 或 `【重磅合作】YYYYMMDD_品牌_合作方_主题.docx`（技术合作·共研/联合实验室）
`【喜报】YYYYMMDD_品牌_奖项_主题.docx`（喜报奖项）
`【活动速递】YYYYMMDD_品牌_活动_看点.docx`（品牌活动）

## 迭代优化机制

每次 AI 产出正文后，用户会对措辞进行手动调整，然后将修改版发回。AI 收到修改版后，执行以下深度对比流程。

### 对比框架：三层分析

每轮迭代必须覆盖三个层级，缺一不可：

| 层级 | 分析内容 | 核心问题 |
|------|---------|---------|
| **一、切入点** | 开篇类型选择（事件宣告/数据引爆/趋势叙事/问题切入/直接宣告/高层引语/产业命题切入/国际背景切入/合作方背景增值，详见行文措辞 §九）、第一段句子顺序、品牌登场时机 | 为什么用了这种切入而不是另一种？第一段信息排列对不对？ |
| **二、大纲** | 章节结构、段落划分、信息优先级、小标题取舍 | 产品技术是合并成章还是拆成独立段？合作信息排在什么位置？行业分析在第几段？结尾是什么收束模式？ |
| **三、逐段表述** | 每段的句式、动词、词汇、衔接、段长 | 终稿改了哪些字词？改的原因是什么？ |

### Step A — 切入点对比

对比两版的：
- 切入点类型是否一致
- 第一段每句话的功能（时间/地点/产品/玩家/合作）
- 品牌在第几个字登场
- 有无多余铺垫/垫话/否定句

输出格式：

```
### 一、切入点对比

| | 我的版本 | 终稿 |
|---|---------|------|
| 切入点类型 | ... | ... |
| 第一句 | ... | ... |
| 差异 | ... | ... |
```

### Step B — 大纲对比

列出两版的完整大纲结构（章节标题 + 每节内容概要），逐项对比：
- 章节数量、有无小标题
- 每节段落数、信息密度
- 信息优先级排序（产品/合作/行业/结尾的先后位置）

输出格式：

```
### 二、大纲对比

**我的大纲：**
1. ...
2. ...
**终稿大纲：**
1. ...
2. ...
**大纲层差异：** 表格逐项对比
```

### Step C — 逐段表述对比 + 修改调整

以每个自然段为粒度，逐段对比。**每段对比必须包含"修改调整"列**，说清楚如果要改应该怎么改：

```
### 三、逐段表述对比

#### 第N段 — XX内容

| | 我的版本 | 终稿 | 修改调整 |
|---|---------|------|---------|
| 关键句 | ... | ... | [改什么、改成什么] |
| ... |
| 差异 | [此段总结] |

#### 第N+1段 ...
```

"修改调整"列为必填列，不能为空。即使某段无需改动，也必须明确写"保持不变"。

差异分类沿用以下维度：

| 维度 | 典型改动 | 判读标准 |
|------|---------|---------|
| **动词升级** | 弱动词 → 强动词 | `references/行文措辞说明文档.md` 动词规范 |
| **句式重组** | 碎句合并、语序调整、信息密度 | 信息密度 / 长句推进模式 |
| **词汇替换** | 普通词 → 行业权威词/四字格 | 词汇策略分类 |
| **衔接优化** | 段落间过渡调整 | 段落衔接手段 |
| **禁用词消除** | 删弱化词、虚词、破折号 | 禁忌清单 |
| **声线校准** | 语气、自信度、叙事距离 | 声线定位 |
| **套路破除** | 打破 AI 模板化表达 | 风格指南未覆盖的机械套路 |
| **新增模式** | 用户使用了未记录的表达方式 | 是否可复用 |

### Step D — 汇总

对比完成后，输出汇总表：

```
### 四、汇总

| # | 规则 | 是否已有 | 更新位置 |
|---|------|---------|---------|
| 1 | ... | 是/否 | 行文措辞 / XX骨架 / 项目说明 / 不写入 |
```

### Step E — 反推风格指南优化

对每条新发现，明确回答：
1. **这是对已有规则的违反，还是新规则的缺失？**
2. **这是单次偏好，还是可复用的模式？**（同类改动 ≥2 次才提炼为通用规则）
3. **这条规则写入哪个文件、哪个章节？**

规则落点判断：

| 规则类型 | 写入文件 |
|---------|---------|
| 声线/句式/词汇/衔接/禁忌 | `references/行文措辞说明文档.md` |
| 写作红线/高频错误/流程规范 | `项目说明文档.md` |
| 骨架变体/产品模板/自查 Checklist | `references/XX类型-切入策划与大纲规范.md` |
| 单次偏好、不具复用性 | 不写入 |

### Step F — 输出更新清单

```
## 更新清单

| # | 规则 | 写入文件 | 章节 | 状态 |
|---|------|---------|------|------|
| 1 | ... | ... | ... | 待确认/已写入 |
```

用户逐条确认后一次性执行写入。

### 四、AI 自查项更新

（如果有需要加入 Checklist 的检查项，列出）
```

用户确认后，AI 将获准的更新写入 `references/行文措辞说明文档.md` 和对应骨架文件的 Checklist。

> **核心原则**：AI 不能自己决定改风格指南——必须通过对比报告让用户看到改动依据，用户确认后再写入。但 AI 必须**主动执行 Step A-C**，不等用户推动。
